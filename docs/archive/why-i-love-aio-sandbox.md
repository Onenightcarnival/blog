# 为什么我很喜欢 AIO Sandbox

最近用 Codex 的定时任务跑 skill，体验有点拧巴。

Codex App 跑在本机，所以权限不能随便放开。给它最大权限不合适，等于把本机文件、网络、命令执行都交出去。但保持默认权限，子 agent 又会频繁停下来问：能不能联网、能不能跑命令、能不能访问某个目录。

临时对话里，这种确认还能接受。人在旁边，看一眼，点一下，继续。定时任务不一样。它本来就应该没人看着也能跑。结果半夜任务启动，子 agent 卡在一个网络权限上，早上起来看才发现什么都没做。

还遇到过另一类问题：沙箱里的网络配置和本机有差异，爬虫脚本跑不起来。agent 只能说环境不允许，或者网络有问题。脚本本身没变，skill 也没变，但执行环境换了一个小细节，事情就断了。

与其依赖 agent 客户端内置的沙箱，不如把执行环境单独拎出来，放到一个能固定配置、能挂持久化卷、能自己决定什么时候升级的地方。

[AIO Sandbox](https://github.com/agent-infra/sandbox) 就是这种东西。它是一个 Docker 容器，里面有 Browser、Shell、File、MCP、VSCode Server，共用一份文件系统。agent 客户端通过 MCP 连进去，调用它的浏览器、终端和文件能力。

它不绑在某个 agent 客户端里。

## 内置沙箱适合临时对话

内置沙箱当然有用。打开 Codex，问几句，跑一段代码，看个结果，这种用法里它很顺手。

它不用配置，不用起容器，不用想端口和挂载目录。权限提示当场弹出来，当场处理。它跟当前工作目录贴得很近，生成的文件也容易打开看。拿来做一次性工作间，很合适。

但定时任务和长期 skill 不是一次性工作间。

skill 一旦挂到定时任务里，就有点像一条小流水线。它需要按点启动，需要没人值守，需要遇到固定输入后给出固定输出。这里最怕的不是多配一次环境，而是今天能跑、明天突然卡住。

客户端内置沙箱在这里有两个麻烦。

第一，权限确认会打断自动任务。子 agent 问一次网络权限，任务就停一次。对话里这是安全检查；定时任务里就是卡点。

第二，客户端自己会更新。更新当然是好事，但更新时也可能改掉内置沙箱：网络策略、权限默认值、工具路径、系统依赖，都可能跟着变。skill 没动一行，运行环境却被换过一轮。问题排查起来很烦，因为变化发生在客户端里面。

更合适的关系是：agent 客户端负责调度和思考，执行环境由使用者自己固定。

## 独立沙箱把环境交给使用者

AIO Sandbox 把执行环境从客户端里拆了出来。

它不是某个 agent 客户端的附属功能，而是一个单独跑起来的容器。版本可以钉住，配置可以写清楚，什么时候升级也能自己决定。网络、代理、DNS、端口、卷挂载，都可以落到 Docker 配置里。

长期跑 skill，很需要这一点。

前面写过，skill 的可移植性不只取决于 `SKILL.md`，还取决于模型、agent harness 和运行环境。模型会变，harness 也会变。真正比较能控制的是运行环境。

AIO Sandbox 固定的是这一块。它不能让所有 agent 表现完全一致，也不能保证模型每次都做同样判断。但 Python、Node、浏览器、文件系统、网络配置这些东西，至少可以稳定一些。

这已经能少掉很多没必要的随机性。

## 持久化卷让沙箱变成工作台

内置沙箱常常是跟着一次对话走的。这个 agent 下载的文件，另一个 agent 不一定能看到；这个任务里产生的 cookie、缓存和中间文件，下次任务也不一定还在。

AIO Sandbox 挂上持久化卷之后，感觉就不一样了。

文件可以留在固定目录里。浏览器下载的东西、脚本生成的中间产物、项目依赖、配置文件，都可以跨任务保留下来。容器坏了可以删，数据不一定要删。

这对多 agent 工作流也很有用。今天 Codex 跑出来的文件，明天可以让另一个 agent 接着读。一个 agent 用浏览器拿到的页面和缓存，另一个 agent 可以在同一个文件系统里处理。沙箱不需要关心对面是谁，它只管当好一个稳定的工作台。

外挂沙箱的好处就在这里：agent 变回工具，沙箱变成公共环境。

## 它也是一台更轻的隔离开发机

这不只和 agent 有关。

在还没有 ChatGPT 的时候，做传统软件开发也经常需要一台隔离的 Linux 环境。最朴素的办法是准备一台单独物理机。权限可以放开，环境可以随便折腾，坏了也不影响主力机器。

但物理机太重。占地方，要维护，要同步文件，重装系统也麻烦。

后来大家用虚拟机和 Docker，就是为了少折腾物理机。开发环境不污染本机，弄坏了也能重来。

AIO Sandbox 是一个 Docker 镜像。启动快，重建快，也容易挂载目录。需要一台干净 Linux 环境时，直接起一个容器；要保留项目和状态，就挂一个卷。

它对人工开发也有用。比如临时试一个依赖很多的项目，跑一个不想装到本机的工具，或者验证一段需要 Linux 环境的脚本。以前要在本机、VM、普通容器之间自己折腾。AIO Sandbox 把常用工具打包好了，起一个容器就能用。

到了 agent 时代，这个好处又多了一层：这台轻量开发机不只给人用，也可以给模型用。

## 给模型一台可重建的 Linux computer

computer use 这类用法，需要一台能看屏幕、点鼠标、跑浏览器和终端的电脑。

如果直接让 agent 在本机上做这些事，需要很谨慎。权限太大，风险也太大。但如果这台“电脑”是一个独立容器，边界就清楚多了。

AIO Sandbox 里有浏览器、终端、VSCode Server 和文件系统。配上持久化卷之后，它就像一台可以长期使用、又可以随时重建的 Linux computer。

模型可以在里面下载文件、跑脚本、打开网页、改项目。搞坏了容器，就重建。真正要留下的东西放在卷里。环境本身是可丢弃的，数据和状态可以选择性保留。

有了这个模式，agent 可以更放开手脚。风险还在，但被关在一个更容易理解、更容易重置的地方。

## 独立才是重点

如果只是临时对话，内置沙箱已经够好。没必要为了显得专业，给每次小实验都起一个独立容器。

但这里的主要痛点不是临时对话，而是长期 skill、定时任务、多 agent 复用，以及给模型一个可恢复的 Linux 环境。

这些用法里，执行环境不应该跟着某个客户端的版本节奏走。客户端可以更新，模型可以替换，agent 工具也可以换来换去，但沙箱最好稳定留在那里。

Browser、Shell、File、MCP、VSCode Server 放在一个容器里，当然方便。但 AIO Sandbox 更重要的地方是，它把执行环境从 agent 客户端里拆出来了。

环境一独立，权限、版本、文件、网络和长期状态才更容易自己掌握。
