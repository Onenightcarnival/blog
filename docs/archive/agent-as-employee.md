# agent 的稳定抽象，可能就是一个打工人

agent 这两年的定义换得很快。

最早讲 agent，比较接近"会用工具的动物"。一个模型，能调几个 function，能跑个 loop，就叫 agent 了。这个定义有点像石器时代的人类学：人之所以是人，因为人会拿石头砸果子。

这个定义不算错，但太单薄。它只描述了 agent 能做事，没描述 agent 是谁。

skill 出来之后，我隐约觉得抽象稳了一些。再加上持久化沙箱、长期记忆、模型分级这些东西，agent 终于不像一只会拿工具的动物，而像一个完整的打工人。

## 从石器时代到人力资源

把 agent 当打工人看，整张图突然就齐了。

- 系统提示词，其实是 JD。它写清楚这个岗位干什么、汇报给谁、什么该做、什么不该碰。
- skill，是这个人会的具体技能。会做 PPT，会写 SQL，会爬数据，会做财报。一个 skill 就是简历上的一条。
- 基础模型，像候选人的资历和能力水平。Opus 像资深专家，Haiku 像初级员工，Sonnet 介于中间。岗位和能力得匹配，不然要么成本太高，要么容易出错。
- 长期记忆，是职业履历。这个人之前做过什么、踩过什么坑、客户偏好是什么，都会记下来，跳槽也能带走。
- 带持久化卷的 AIO Sandbox，是打工人的电脑。文件、缓存、配置、半成品工程，都在这台机器上。换一份工作可以换电脑，但这台机器本身是稳定的工作环境。

这套抽象比"会用工具的模型"更完整。它关心的不只是 agent 能做什么，还包括它在哪个岗位上，带着什么技能和履历干活。

## JD 没写清楚，模型再强也没用

换到人力资源视角看，很多 agent 跑不好，问题不一定出在模型上，而是出在岗位定义和用人方式上。

最常见的一种失败，是 JD 没写清楚。系统提示词里岗位职责模糊，权限边界没说清，不该做的事也没列出来。模型只能自己猜。猜对了像经验丰富的员工，猜错了就容易越界做决定。

第二种失败，是能力和岗位错配。让 Opus 去做一份每天跑一次的格式转换，成本太高。让 Haiku 去做需要长链推理的研究任务，又容易出错。

第三种失败，是简历和岗位错配。skill 装了一堆但没一个跟 JD 对得上。或者 JD 要求做数据分析，结果这个人 skill 列表里全是 PPT 模板。

这些问题在传统软件工程里不太会出现，因为函数和参数是写死的。但 agent 会按岗位描述行动，岗位描述本身就成了关键工程问题。

写 prompt 不再是写 prompt，是写 JD。

## 打工人需要一台自己的电脑

一个打工人要稳定干活，最好有一台在职期间能一直用的电脑。

这台电脑不一定跟着人一辈子走，但在这份工作里，它应该是稳定的。文件放在哪里，依赖装在哪里，半成品工程在哪里，都得有个固定位置。否则每天上班都像临时借一台机器，今天调好的环境，明天又要重来。

早期 agent 就很像没有自己电脑的人。它要么借用户的终端，要么借某个客户端的内置沙箱。每次对话起一个新环境，结束就清掉，下次再从头开始。

这种用法适合临时活，但很难积累。今天下载的文件，明天看不到；今天调好的环境，明天又得调一遍；今天产出的中间结果，明天没法接着用。

给 agent 配一台带持久化卷的沙箱，性质就变了。它像有了一台在职期间稳定可用的工作电脑。容器可以重建，但卷里的文件、缓存、配置和半成品工程还在，今天的工作可以接到明天。

这个变化看着小，其实是从"做完就走"变成"长期在岗"。一个长期在岗的 agent，可以承担更复杂的任务，可以和别的 agent 协作，也可以慢慢攒下属于这个岗位的资料、脚本、配置和半成品。

## skill 要像证书一样可验证

从技术上看，skill 的可移植性要靠这些细节：依赖怎么锁，运行环境怎么固定，命令怎么复现。

换到人力资源视角，skill 的角色其实更清楚了。它先是简历上的技能条目，但如果要跨 agent、跨环境复用，就得像证书一样可验证。

证书的价值，在于换公司、换岗位，别人也知道它能干什么。一个会做 PPT 的人，去哪家公司都能做 PPT。一份合格的 skill，也应该这样——挂到不同的 agent 上、不同的运行框架里、不同的模型下，效果不会差太远。

skill 不只是 prompt 的延伸。它更像简历上的可迁移资产。这个人换公司、换 JD、换电脑，只要 skill 还在，这项本事就还在。

这也是为什么 skill 要按工程项目写，而不是当成一段说明文档。它得有可验证的内容，否则别人很难相信它真的能用。

## 抽象稳定下来之后

这样看，agent 的工程问题就不再只是怎么调工具、怎么写 loop。

先把岗位说清楚，再选合适的模型，给它稳定的工作环境，把 skill 写成可验证、可迁移的东西。几个问题看起来分散，其实都在回答同一件事：这个 agent 到底是谁，要负责什么，又靠什么把活干完。

agent 不只是会用工具的模型。它有岗位、有技能、有工作环境，也会留下履历。

把这件事想清楚之后，剩下的工作其实和管理一个团队没太大区别。
