# agent 长坏了，还可以重装

DeepSeek Harness（dsh）发布才一周，这一周我给它打包了一个桌面版。做的过程中踩过一次坑：我让 agent 自己改 dsh 的插件，改完实时生效，一切正常。关掉 dsh 再启动，服务直接报错，起不来了。那一刻 agent 已经不在了——它跑在那个起不来的进程里。最后的解法没有任何技术含量：重装。

桌面版的几个设计决定都是从这次起不来开始的：配置修改统一由 Electron 壳代管，MCP、skill、上下文压缩这些常用配置都走图形界面这条确定性路径；预置插件只挑了几个和内核测试过的，构建期锁死。agent 不碰自己的 harness。

做完这个项目，正好把背后的想法写清楚：自演进这件事，我认为该发生在哪一层。

## DeepSeek 的答案：连 harness 一起演进

DeepSeek 对 agent 的定义是 model + harness。顺着这个定义，他们的自演进方案很彻底：模型之外的一切也可以动。cordis 微内核加插件的架构，内核尽量小，能力全部做成插件，插件可以在运行时装卸、替换、升级——理论上 agent 可以一边跑一边给自己换零件。

这个方案不是没道理。微内核的思路和操作系统一样：把必须冻结的部分缩到最小，其余都做成可换的。分歧不在「要不要有不可变的核」——所有人都同意要有——而在两个地方：这个核画多大；换零件这个动作由谁执行，确定性的代码，还是 agent 自己的概率推理。

我的实操结论是：核要画大，把整个 harness 圈进去；换零件不走推理回路。演进落在 skill 层。

开头那次起不来，说明了为什么换零件不能走推理回路。实时生效是最有欺骗性的反馈：agent 改完看到的是内存里的状态，进程还在跑，加载过的模块还在，它据此判断「改成功了」。真正被改坏的是磁盘上那份，要等下一次冷启动才暴露。而冷启动失败的时候 agent 不在场——它就住在那个起不来的进程里。你没法让一个起不来的 harness 里的 agent 去修这个 harness，只能人来收拾。agent 对自己 harness 的修改，恰好在它最需要看见结果的地方看不见结果。

但这还不是主要原因。主要原因不在恢复有多难——恰恰相反，是恢复太容易了。

## 卸载重装，是人没有的特权

agent 和人最大的差别，是 agent 可以下线，重新部署一个。程序改坏了，卸载重装，十分钟后一个干净的实例又站起来了。

人不能卸载重装。经历、观念、损伤都长在同一具身体里，没有快照，没有导出按钮，走过的路径全部不可逆。一个人长坏了，没有任何机制能把他退回三年前的版本。所以人类对不可逆的自我实验极其谨慎，也应该谨慎。

agent 没有这个包袱。试错、长坏、推倒重来，成本只是一次重新部署。这是自演进在 agent 身上成立、在人身上不成立的根本原因。

但这个特权同时改变了问题。既然重装兜底永远存在，「改坏了怎么办」就不是自演进的核心问题——答案永远是重装。核心问题是另一个：重装之后，能留下什么。

重装是毁灭性回滚，程序层的一切都会被抹掉。如果演进成果长在 harness 里——运行时换掉的插件、改过的内核逻辑、动态调整的执行回路——那每次改坏重装，成果跟着故障一起归零。这样的演进永远在从头再来，攒不下东西。

skill 不一样。skill 是文件，是数据，和程序本体分离。dsh 的数据和配置放在用户目录 `~/.dsh` 下，内核装在 `runtimes/<版本>/` 里，新内核启动失败会自动回退内置版本。内核可以反复重装、升级、回滚，`~/.dsh` 里的东西一直都在。重装 Word 不会丢你的文档。

所以 skill 这条路靠谱，「不容易把自己改坏」只是表面，根本原因是 skill 能穿越重装。演进成果放在能穿越重装的那一层，重装才能从灾难恢复变成日常操作——坏了就扔，扔了不心疼，因为攒下的东西不在被扔掉的部分里。

## 演进要写进基因，不要写进肉身

生物演化能运转，靠的正是这个结构：身体是一次性的，基因是传下去的。一只动物后天练出来的肌肉、学会的本事、受过的伤，都留在它自己身上，随着它一起死掉；能传给下一代的只有基因。演化从来不发生在某一只动物身上——单个个体只负责活一遍、试一遍，然后被留下或者淘汰，真正往前走的是基因。

对应到 agent：实例是那只动物，随时可以销毁重建；skill 是基因，穿越实例存续。一个实例跑砸了，杀掉，新实例带着同一套 skill 起来，上一代攒下的能力一点不少。

harness 自改是另一条路：把演进成果写进实例的身体里，指望下一个实例直接继承——就像指望长颈鹿伸了一辈子脖子，生下来的孩子脖子就长。这个想法在生物学史上有过名字，叫拉马克主义，后来被证明不是演化的工作方式：后天练出来的东西，基本传不进基因。生物界没走这条路，我不认为 agent 需要重新试一遍。

人的困境也可以用这个框架说清：人的状态和本体不可分离，没有程序和数据之分。你不能只重装身体、保留记忆，也不能只导出记忆、换个身体。所以人类的演化只能在一代又一代的群体层面发生，单个人没有回滚。agent 是第一种单个实例就能演化的东西——前提是架构上把程序和数据分开了。

说到这里，自演进的设计问题可以收成一句话：划清什么算程序、什么算数据，然后让演进只发生在数据层。程序层保持出厂状态，随时可重装；数据层承接一切积累，穿越每次重装。

划分的标准也不复杂：启动时要加载的，算程序；跑起来之后才读的，算数据。插件是 harness 启动时加载的代码，改坏了启动就失败，所以它是程序层——这正是开头那次事故的全部原因。skill 是 harness 跑起来之后按需读的文件，启动不依赖它，一个 skill 写坏了，最多是那个任务做砸，服务照常起来。

## 两个边界

这套框架有两个地方不能想得太美。

第一，重装只回滚 agent，不回滚世界。agent 发出去的消息、提交的代码、改过的线上配置，不会因为实例重装而消失。数据能穿越重装是好事，但泄漏到世界里的 state 同样穿越了——好的坏的都算。所以自演进的安全性只覆盖 agent 内部，动作层的护栏一样都不能省。

第二，skill 层也会慢性长坏。单个 skill 随时可删，但积累 skill 的过程会漂移：坏习惯被一次次成功强化，记忆被注入污染，错误的经验写成了「最佳实践」。基因也不是攒下来就完事，还得经过筛选。所以数据层的演进不能只有积累，还得有淘汰：evals 当体检，来源记录当追溯，定期审查哪些 skill 该留、哪些该删。不知道什么时候坏的，就谈不上退回去。

---

把变化收进可以整体丢弃的实例里去试，把值得留下的写进能穿越重装的数据层——这是我理解的自演进。agent 比人幸运的地方就在这里：它的每一次长坏都有退路。设计自演进机制的全部工作，是别亲手把这条退路焊死。
